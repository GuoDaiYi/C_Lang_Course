# C 语言入门项目（零基础）

这是一个专门给 **完全新手** 准备的 C 语言学习项目。

特点很简单：

- 一个文件只讲一个知识点，代码里的注释是中文，边看边跑。
- **每一课的注释本身就是一份讲义**：开头写清楚「这节课解决什么问题」「学之前要先会什么」，
  正文的每一段代码前都有一段导读，告诉你这段在干嘛、跑起来会看到什么。
- 每节课都能单独编译、单独运行，不用等前面的课全部学完。
- 有练习（带参考答案），最后还有两个可以真正玩起来的小程序。
- 所有文件都只用标准 C，不加任何第三方库，装了编译器就能跑。

## 项目结构

```
c-tutorial/
├── README.md       本文件：环境准备、学习路线、常见报错排查、文件清理指南
├── CHEATSHEET.md   语法速查表（写代码时放在旁边查）
├── Makefile        一条命令就能编译和运行（make clean / make tidy 清理垃圾）
├── .gitignore      告诉 git 哪些是编译产物、不要提交
├── lessons/        16 节课，每节课一个文件
├── exercises/      5 个练习，solutions/ 里是参考答案
└── projects/       2 个综合小项目（猜数字、成绩管理器）
```

> 课程分两部分：第 01~12 课是**主线**（语言基础），
> 第 13~16 课是 **math.h 数学函数专题**，想先把基础打牢可以之后再回来学。

## 0. 先看这里：每一课长什么样

整套课的每个 `.c` 文件都是同一个结构。**打开任何一课，你都会看到下面这 6 块**，
从前往后读就行，不用跳着看：

| 位置 | 这一块叫什么 | 讲什么 | 怎么用 |
| --- | --- | --- | --- |
| 文件最开头 | ▶ 这节课要解决什么问题 | 用大白话说为什么要学这个、学完能做什么 | 先读这 3~5 行，心里有个目标 |
| 文件最开头 | ▶ 学这节课之前，你需要已经会 | **前置知识**：列出依赖哪几课、有个开课自测 | 自测答不上来，先回去补 |
| 文件最开头 | ▶ 本节课新出现的语法 | 把这课新东西集中列一张表（写法/读法/作用/坑） | 扫一眼，学到那就会懂 |
| 文件最开头 | ▶ 怎么读这个文件 | 告诉你下面该怎么读 | 看完这段就开始看代码 |
| 正文每段代码前 | ▶▶▶ 第 N 段 | 这段代码在干嘛、用到新语法吗、**预期输出是什么** | 边看边在脑子里预演输出 |
| 文件最末尾 | ▶ 动手练习 | 4~5 道改代码/写代码的题，每题带提示和验收标准 | 做完再往下看 |
| 文件最末尾 | ▶ 本课常见报错速查 | 这一课真会遇到的报错 + 原因 + 修法 | 卡住时回来查 |
| 文件最末尾 | ▶ 自测题答案 | 对应开头「开课自测」的答案 | 自测完再对答案 |
| 文件最末尾 | ▶ 本课小结 / 下一课预告 | 回顾要点 + 预告下一课 | 收尾 |

**为什么要这么设计**：新手最常见的问题不是「看不懂某一行代码」，而是
「不知道现在该看哪一行、为什么这里要这么写、跑出来会对不对」。
所以每段代码都配了「预期输出」，让你在运行之前先自己推一遍——
推对了，说明你真懂了；推错了，正好发现你的理解漏洞。

### 遇到「预告」不要慌

课程严格遵守**「一课只讲一课的东西」**：一节课里出现的语法，只会用到它自己和
前面几课已经教过的。所以你会看到一些课**故意不出现**某些你迟早要学的东西：

| 你在第几课 | 故意先不出现 | 出现在 |
| --- | --- | --- |
| 03 输入 | `if`（做输入校验） | 第 4 课 |
| 04 条件 | 数组、循环、函数 | 第 6/7/8 课 |
| 05 switch | 循环、函数、数组 | 第 6/7/8 课 |
| 09 字符串 | 指针的细节 | 第 10 课 |

这些「还没学的东西」会以**「预告」注释**的形式出现在代码旁边，
讲清楚它以后会变成什么样、对应第几课。学完那一课再回来把它打开就行。

这样做的好处是：你不会在第 3 课就被一个看不懂的 `if` 绊住，
也不用提前背后面才用得上的语法。

## 2. 编译和运行

**核心只有两条命令**，记住这个就够用了：

```bash
cc 源文件.c -o 可执行文件    # 编译：把源代码翻译成机器能跑的程序
./可执行文件                  # 运行（Windows 上是 可执行文件.exe）
```

比如第 1 课：

```bash
cd /Users/guodaiyi/Documents/C语言新手课/chu/outputs/c-tutorial   # 换成你自己的路径
cc lessons/01_hello_world.c -o hello
./hello
```

> 路径里的中文和空格都不影响使用，但**路径要加引号**更保险：
> `cd "/Users/你的名字/我的 课程/c-tutorial"`

### 用 Makefile 偷懒（推荐）

项目里已经写好了 `Makefile`，可以省掉每次敲长命令：

```bash
make                                  # 编译所有课程、练习和项目
make run L=lessons/01_hello_world     # 编译并运行某一课（不用写 .c）
make run L=lessons/06_loops           # 换一课
make run L=lessons/05_switch          # switch 专题课
make run L=lessons/13_math_basics     # 数学专题课
make run L=projects/guess_number      # 运行猜数字小游戏
make list                             # 看看有哪些程序可以运行
make clean                            # 删掉生成的文件，重新开始
make help                             # 忘了命令时看一眼
```

> 编译出来的程序都会放在 `build/` 目录里，源文件不会被改动。

### 编译数学函数课：别忘了 -lm

第 13~16 课用了 `math.h` 里的 `sqrt`、`pow` 这些函数。它们放在一个单独的
数学库里，手动编译时**Linux 上必须加 `-lm`**：

```bash
cc lessons/13_math_basics.c -o math_demo -lm
```

macOS 上不加也能过（系统库已经包含），但统一加上更省心。
本项目的 `Makefile` 已经把 `-lm` 配好了，用 `make` 就不用管这件事。

少了 `-lm` 会看到这样的报错：

```
Undefined symbols for architecture x86_64:
  "_sqrt", referenced from:
     ...
ld: symbol(s) not found for architecture x86_64
```

意思是「找不到 sqrt 这个函数」，不是你的代码写错了，编译命令补上 `-lm` 就行。

### 加警告选项（强烈建议）

新手最容易犯的错是「程序能编译，但结果是错的」。让编译器帮你抓：

```bash
cc -Wall -Wextra -std=c11 lessons/04_conditions.c -o cond
```

`-Wall -Wextra` 打开警告，`-std=c11` 指定用 C11 标准。**警告要当成错误来看**，
它经常指出真正的 bug（比如忘了写 `&`、变量没初始化）。

### 每节课怎么学（推荐流程）

一节课按下面 6 步走，大概 30~60 分钟。**不要跳过第 1 步和第 4 步**——
新手最大的浪费就是「直接抄着改一遍，输出对了就走」。

| 步骤 | 做什么 | 大概花多久 | 目的 |
| --- | --- | --- | --- |
| 1️⃣ | 读文件开头的「这节课要解决什么问题」+「前置知识」 | 5 分钟 | 知道为什么要学，自测不过就先补前置课 |
| 2️⃣ | 读「本节课新出现的语法」那张表 | 5 分钟 | 建立词汇表，看不懂先跳过 |
| 3️⃣ | **逐段读代码**：每段先看「▶▶▶ 第 N 段」说这段要干什么，再看代码 | 15 分钟 | 理解每一段的存在理由 |
| 4️⃣ | **预演输出**：看到「预期输出」时先自己猜一遍，再往下走 | 10 分钟 | 检验理解是否到位 |
| 5️⃣ | 编译运行，把真实输出和「预期输出」对一遍 | 5 分钟 | 不一致就回去精读那一段 |
| 6️⃣ | 做「动手练习」+ 对「自测题答案」 | 15~30 分钟 | 把知识变成手感 |

**一个重要习惯**：第 4 步的「预演输出」是整套课最值钱的部分。
先猜再运行，和直接运行看结果，效果差 10 倍。

### 卡住了怎么办

按这个顺序排查，**不要跳过第 3 步**：

1. 看当前课文件末尾的「▶ 本课常见报错速查」——80% 的问题这一节里就有。
2. 看本文件 `README.md` 第 6 节的全局报错对照表。
3. 看 `CHEATSHEET.md` 查语法。
4. 还不懂，就在**下一段代码**前面加一句 `printf` 把变量的值打出来，
   看它是不是你以为的那样——这是最实用的调试手段。
5. 实在卡住，**先跳过这节课**，把后面的基础课学完再回来。
   卡住不代表你笨，很多时候只是前置知识没铺够。

## 6. 新手最常见的报错与排查

> **先查你当前那一课**：每个课程文件末尾都有一节「▶ 本课常见报错速查」，
> 写的是这一课真会遇到的问题。80% 的情况在那里就能解决。
> 下面是跨所有课通用的总表。

| 现象 | 原因 | 怎么修 |
| --- | --- | --- |
| `error: expected ';' before ...` | 上一行忘了分号 | 看报错行号的**上一行**，补 `;` |
| `warning: format '%d' expects ...` | `printf` / `scanf` 的格式符和变量类型不匹配 | `int` 用 `%d`，`double` 用 `%lf`，`char` 用 `%c`，字符串用 `%s` |
| 输入的数字是个奇怪的巨大值 | `scanf("%d", n)` 少了 `&` | 写成 `scanf("%d", &n)` |
| `Segmentation fault`（段错误） | 访问了不存在的内存：数组越界、用空指针、`scanf` 少了 `&` | 检查下标是否 `< 长度`；检查文件/指针是否为 `NULL` |
| 结果算出来是整数，小数被丢掉了 | `int / int` 得到整数 | 至少把一边写成小数：`5.0 / 2` |
| `implicit declaration of function 'xxx'` | 忘了 `#include` 或者函数写在调用之后 | 补上头文件，或在使用前声明函数 |
| `Undefined symbols ... "_sqrt"` | 用了 `math.h` 的函数，但链接时没带上数学库 | 编译命令末尾加 `-lm`（第 13 课） |
| 编译报 `M_PI` 没有定义 | `M_PI` 不是标准 C，各平台给不给看系统 | 自己定义一个：`#define M_PI 3.14159265358979323846`（第 13 课） |
| `sin(30)` 算出来不是 0.5 | 三角函数收的是**弧度**，不是角度 | 先换算：`sin(30.0 * M_PI / 180.0)`（第 14 课） |
| 选了选项 2，却把选项 3 的内容也打印了 | `switch` 里忘了写 `break`，程序「贯穿执行」了 | 每个 `case` 结尾都补上 `break`（第 5 课） |
| `error: case label does not reduce to a constant expression` | `case` 后面写了变量 | `case` 后面只能跟常量，比如 `case 1:`、`case 'a':` |
| 输出没有换行、挤在一起 | 忘了 `\n` | 在 `printf` 字符串结尾加 `\n` |
| `make: command not found` | 没装 make（Windows 上常见） | 直接用 `cc 文件.c -o 程序` 编译，或装 MSYS2 |
| 编译报 `warning: ... within block comment` | 注释里写了「星号 + 斜杠」，把注释提前关掉了 | 把注释里那两个字用文字描述，比如「星号加斜杠」 |
| `error: '/*' within block comment` 或一堆莫名其妙的错 | 同上，注释被提前关闭，后面的文字被当成代码 | 搜一下注释里的 `*/`，改成文字描述 |
| 程序卡住不退出 | 死循环（循环条件永远为真） | 按 `Ctrl+C` 强制结束，检查循环体里有没有让条件变假的语句 |
| 输出的小数和课里写的不一样 | 浮点运算有精度误差，不同系统最后一位可能差一点点 | 正常现象，对比时别盯最后一位小数 |

调试小技巧：

```bash
cc -g lessons/06_loops.c -o loop   # -g 加上调试信息
```

最实用的调试手段其实是 `printf`：在关键位置打印变量的值，看它是不是你以为的那样。
比如循环里加一句 `printf("i=%d\n", i);`，就能立刻看出循环跑到哪儿停住了。

## 8. 文件清理指南（怎么让这个项目一直保持干净）

学 C 的过程中会不停产生新文件：编译出来的可执行程序、程序跑出来的数据文件、
macOS 偷偷塞进去的 `.DS_Store`……时间一长目录就被垃圾淹了，
`ls` 一看全是自己看不懂的东西，最容易打击学习热情。

这个项目用一套很简单的规则保持干净。

### 判断的唯一标准

> **删掉之后，跑一条命令能不能重新造出来？**
>
> 能　→ 是产物，放心删
> 不能 → 是你写的代码或文档，**绝对不能删**

### 文件分类表

| 分类 | 具体文件 | 能删吗 | 怎么重新生成 |
| --- | --- | --- | --- |
| **你的代码** | `lessons/*.c`、`exercises/**/*.c`、`projects/*.c` | ❌ **不能删** | 这就是课程本体 |
| **你要查的文档** | `README.md`、`CHEATSHEET.md` | ❌ **不能删** | 手写的，删了就没了 |
| **编译产物** | `build/` 整个目录、源码目录里没有扩展名的可执行文件 | ✅ 可以删 | `make` |
| **调试符号包** | `*.dSYM/` | ✅ 可以删 | `make`（编译带 `-g` 时会重新生成） |
| **macOS 垃圾** | `.DS_Store` | ✅ 可以删 | Finder 会自动再建，删了还会回来 |
| **运行时数据** | `students.txt`、`report.txt`、`gradebook.txt` | ✅ 可以删 | 跑第 12 课或成绩管理器就会重新生成 |
| **编辑器临时文件** | `*~`、`*.bak`、`*.swp` | ✅ 可以删 | 编辑器自己会生成 |

### 一条命令清理干净

```bash
make clean    # 只删编译产物（build/ 目录）
make tidy     # 彻底清理：编译产物 + 散落的可执行文件 + *.dSYM + .DS_Store + 运行时数据文件
```

`make tidy` 跑完，**源码和文档一个都不会少**，可以立刻 `make` 重新编译。

工作区根目录还有几个不在课程目录里的东西（`sandbox/` 的可执行文件等），
在根目录跑这几行：

```bash
cd /Users/guodaiyi/Documents/C语言新手课
find . -name '.DS_Store' -delete
rm -f sandbox/triangle sandbox/tri_prec sandbox/triangle_dirty sandbox/triangle_fixed
```

### 怎么一眼认出「编译产物」

| 特征 | 说明 |
| --- | --- |
| **没有扩展名** | 源码是 `.c`、文档是 `.md`，编译出来的东西没有扩展名 |
| **系统当成程序** | `file xxx` 显示 `Mach-O executable`；在 VS Code 里右键能选「在终端中运行」 |
| **和源文件同名** | `lessons/01_hello_world.c` 旁边那个 `lessons/01_hello_world` 就是它 |
| **删了源码还在** | 删掉后 `make` 一跑就回来了 |

**为什么它会跑到源码目录里去？** 因为手动编译时没给 `-o` 指定输出位置：

```bash
cc lessons/01_hello_world.c -o lessons/01_hello_world            # ❌ 落在源码目录
cc lessons/01_hello_world.c -o build/lessons/01_hello_world     # ✅ 落在 build/
```

用 VS Code 编译时也一样——它的编译任务默认把可执行文件放在源文件旁边
（配置见工作区根目录的 `.vscode/tasks.json`）。

**养成习惯：一律用 `make`；手动编译时把 `-o` 指向 `build/`。**
这样源码目录永远是干净的，只剩 `.c` 文件，一眼就能数清楚。

### `.gitignore` 是干什么的

本项目有两个 `.gitignore`：

- 工作区根目录的 `.gitignore` —— 管整个工作区
- `c-tutorial/.gitignore` —— 管课程目录

它们的作用是告诉 git「这些是垃圾，别记录进版本库」。
有了它，`git status` 里就不会冒出一堆看不懂的可执行文件，提交历史也保持干净。

**以后你自己往课程里加文件时，先问一句：它能重新生成吗？**
能，就加进 `.gitignore`；不能，就正常提交。

### 一个**不要**删的地方：`sandbox/`

工作区里的 `sandbox/` 存着几个**故意写错的 C 程序**，
是新手真实会犯的错的样本：

| 文件 | 演示的错误 |
| --- | --- |
| `bad_semicolon.c` | 用了中文全角分号 `；`，编译器会直接报语法错误 |
| `literal_paste.c` | 直接把 Markdown 里的 `\#include` 复制进代码 |
| `bad_quotes.c` | 引号 / 括号配对错误 |
| `triangle_dirty.c` | `scanf` 失败后，变量里留着没初始化的垃圾值 |
| `triangle_precision.c` | 浮点精度问题（`0.1 + 0.2 != 0.3`） |

想练「读懂编译器报错」的时候，拿这些文件编译一下，看看编译器怎么骂你：

```bash
cc sandbox/bad_semicolon.c -o /tmp/x     # 看看报什么错
sh sandbox/run_tests.sh                  # 顺便对比 triangle 和 triangle_fixed 的行为差异
```

**这些是教学素材，不要删。** 里面编译出来的可执行文件倒是可以随便删。

## 常见问题

**要不要学 C 之前先学 Python？**
不需要。C 让你更清楚地理解「内存、类型、指针」这些底层概念，先学 C 之后再学其他语言会很轻松。

**一定要用 IDE 吗？**
不一定。新手用命令行 + 文本编辑器（VS Code、Sublime、vim 都行）反而更容易搞懂「编译」这件事。

**记不住语法怎么办？**
不用背。看 `CHEATSHEET.md`，需要的时候查就行。真正需要练的是「怎么把问题拆成步骤」。

**一节课要花多久？**
一节 30~60 分钟比较舒服。赶时间的话可以先看「这节课要解决什么问题」和
「本节课新出现的语法」两张表，再直接读代码——但别跳过「动手练习」，
练过和看过，差别是很大的。

**我的输出和文件里写的「预期输出」对不上，是不是我写错了？**
先看是不是小数最后一位的精度差（正常）。如果差很多，多半是漏了 `&`、
格式符写错、或者整数除法没转成小数这三类问题。

**每次都要重新编译吗？**
是的，改完代码就要重新编译一次。`make run L=lessons/01_hello_world` 会自动
「编译 + 运行」两件事，比手敲两条命令省事。

**我卡在某一课很久了，要不要跳过去？**
可以跳。指针（第 10 课）本来就是关卡，跳到第 12 课再回头看第 10 课，
理解会快很多。但「变量/输入/条件/循环/函数/数组」这 6 课是地基，
这几课必须扎实。

**要不要一边学一边做笔记？**
建议做，但别抄代码。抄代码没有意义，把「这课的坑是什么」「我哪里搞错了」
写下来才有价值。每个人踩的坑不一样，你的笔记就是你自己的错题本。

**我目录里一堆看不懂的文件（没有扩展名的、还有 .dSYM 什么的），能删吗？**
能。判断标准只有一条：**删掉之后能不能用一条命令重新造出来**。
能造出来的是产物，放心删；造不出来的是你的代码和文档，别动。
详细的分类表和一条命令清理方法见**第 8 节「文件清理指南」**。

**为什么我的 `lessons/` 目录里多出一个和 `.c` 文件同名的文件？**
那是你编译出来的可执行程序（因为手动编译时没给 `-o` 指定位置）。
直接删掉即可，或者以后直接用 `make`，产物会统一放进 `build/`。
